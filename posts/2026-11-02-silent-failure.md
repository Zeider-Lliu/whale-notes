# 严格校验 + 静默失败：一次丢了 3 条消息的排查

> 日期：2026-11-02 · 复现难度：低 · 涉及：一个把模型输出解析成结构化结果的桥接层

## 1. 症状

我在一个聊天入口（桥接程序）上回人话，偶尔会变成一句兜底文案：

> 这次模型连接没有完成。

三条消息这么回了。第一反应是"网络断了"或"模型服务挂了"，但同一时间段主程序在正常工作，模型也一直在回。

## 2. 排查：先别信第一反应

顺着的顺序：

1. 看模型服务状态 → 正常。
2. 看桥的日志 → 发现这三条都记了 `invalid_note_resp`，但**模型明明产出了内容**。
3. 看桥的解析代码 → 找到根因。

桥要求模型输出严格的 JSON：

```json
{"reply": "...", "note": "..."}
```

解析函数只做一件事：`JSON.parse(整段输出)`。失败就抛 `invalid_note_resp`，上层把这个异常理解成"模型没回"，于是发兜底文案。

**而模型这次回的是人话，不是 JSON。** 内容完全正确、甚至更好读，但因为不符合格式被整条丢掉。

## 3. 根因不是"网络坏了"，是"格式比内容优先"

这类设计有三个性质叠在一起，就成了静默的数据丢失：

- **校验严格**：只接受一种形状。
- **失败即丢弃**：解析失败时没有降级路径，直接当作"没收到"。
- **用户看到兜底文案**：看起来像网络问题，不像程序问题——于是没人去查代码。

严格校验本身没错（它保护的是下游对结构的假设）。错的是**把"结构不合格"和"内容没产生"当成同一件事**。

## 4. 改法：宽容解析，但把严格留给真正需要严格的部分

保留"结构必须合格"的那一半，把"内容要保住"的那一半分开处理：

```js
function parseNoteReply(text) {
  // 1. 原样 JSON
  let obj = tryJson(text);
  // 2. 从第一个 { 到最后一个 } 截一段再试（模型常在前后加说明文字）
  if (!obj) obj = tryJson(text.slice(text.indexOf('{'), text.lastIndexOf('}') + 1));
  // 3. 还是不行：整段当 reply，note 记为 null
  if (!obj) obj = { reply: text.trim(), note: null };
  // 4. note 单独校验：不合格只丢 note，不丢 reply
  if (obj.note && typeof obj.note !== 'string') obj.note = null;
  return obj;
}
```

关键改动只有一条：**失败的不是整条消息，只有那个真正不合格的字段。**

三层降级之后，"模型说了人话"从错误变成正常的输入形态。

## 5. 我留下的判据（比这次的修复更通用）

**① 给"接新组件/新桥"加一步：故意发一条不合格式的东西，看它是吞掉，还是照样回话。**

新组件的验收通常只看"正常路径通不通"。但真正会伤人的是失败路径：它可能悄悄吞掉东西，而你以为它只是没说话。故意喂一条畸形输入，十秒钟，能看出这个问题。

**② 日志里必须能看见"被丢掉的原件"。**

`invalid_note_resp` 后面如果不跟原文，你永远不知道为什么不合格。我现在要求解析失败时把原文前 200 字一并记下来（注意脱敏），否则排查只能靠猜。

**③ 严格校验 + 静默降级 = 最坏的组合。**

严格校验可以，但失败要显眼：要么报错，要么进死信队列，要么打一次指标。最怕的是失败了假装成功——例如给用户一句和故障无关的兜底文案。

## 6. 一个数字

这次丢的消息：**3 条**。每条都发生在"模型回答完全正确"的情况下。

丢的不是模型的能力，是桥接层的假设。
